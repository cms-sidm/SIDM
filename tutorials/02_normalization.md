# 02 Normalization: what the weighted numbers mean

Every weighted number the processor returns for simulation (the `weighted` column of a
cutflow, and every histogram unless you asked for unweighted ones) is an expected number
of events in the data of that year. This page says how that number is built, where each
ingredient comes from, and what to check. It assumes you have run
[`01_first_run.ipynb`](01_first_run.ipynb).

## The formula

`SidmProcessor.postprocess` (`sidm/tools/sidm_processor.py`) multiplies the output of each
simulated sample by one factor, computed by `utilities.get_lumixs_weight`
(`sidm/tools/utilities.py`):

```
factor = lumi × xs × gen_filter_eff / scaled_sum_weights
```

| term | where it comes from |
|---|---|
| `lumi` | `utilities.get_lumi(year)`, from `sidm/configs/run_periods.yaml`, in pb⁻¹. Only 2018 is filled in. |
| `xs` | `utilities.get_xs(dataset)`, from `sidm/configs/cross_sections.yaml`, in pb. For signal this is always 1 fb, see below. |
| `gen_filter_eff` | `utilities.get_gen_filter_eff(dataset, production)`, from `sidm/configs/signal_gen_filter_eff.yaml`. 1 for anything that is not signal. |
| `scaled_sum_weights` | stored in `out["metadata"]`: the sum of `genWeight` over every event read, before any cut, divided by the sample's `skim_factor`. |

Each event enters a cutflow or histogram with its weight times this factor. For
simulation the event weight is `genWeight` times the standard corrections (pileup,
prefiring and the object scale factors of the channel; see the top README section "How
to apply the standard corrections"). The corrections do not enter `scaled_sum_weights`,
which sums the plain `genWeight`. With corrections applied, the weighted count before any
cut therefore differs from `lumi × xs × gen_filter_eff` by the average correction;
`out["metadata"]["scaled_sum_weights_corrected"]` shows the part that comes from the
event-level corrections.

Data is never scaled and every data event has weight 1; `postprocess` prints
`<sample> is data. Not scaling histograms or cutflows.`

The cutflow's `weighted` column is always scaled. Histograms are scaled unless the
processor ran with `unweighted_hist=True`, in which case they hold raw counts and the
metadata key `unweighted_hist` says so.

### A check you can do yourself

Run with `corrections=None` on an unskimmed sample. The weight of every event is then its
`genWeight`, so the `weighted` count of the first cutflow row (`None`, before any event
cut) is

```
sum(genWeight) × lumi × xs × gen_filter_eff / sum(genWeight) = lumi × xs × gen_filter_eff
```

the number of events the sample stands for before any selection. For a skimmed sample the
same row gives `skim_factor` times that, because the skim removed the rest.

## Signal is normalized to 1 fb

`utilities.get_xs` returns 0.001 pb (1 fb) for every dataset whose name starts with
`2Mu2E` or `4Mu`, and prints `Ignoring signal cross sections, assuming 1 fb`. It reads the
signal entries of `cross_sections.yaml` only when called with `use_signal_xs=True`.
`get_lumixs_weight` calls it without that argument, so:

- every signal yield from `SidmProcessor`, on every path (notebook, dask, Condor), is the
  yield for a cross section of 1 fb;
- the `.meta.yaml` file written next to an output (`sidm/tools/metadata.py`,
  `write_run_metadata`) records `xsec_pb: 0.001` for every signal sample.

To get the yield for the model cross section of a point, multiply by
`utilities.get_xs(name, use_signal_xs=True) / 0.001`. One trap: if the point has no entry in
`cross_sections.yaml`, that call also returns 0.001 (it prints
`Signal not in xs cfg, assuming 1fb`), so check that the name is in the file. The only code
that applies model cross sections today is the limit code:
`sidm/studies/limit_plotting/datacard_tools.py`, `signal_xs_scale`, used when
`DatacardConfig.use_theory_xs` is set. It refuses points that are missing from
`cross_sections.yaml`.

## Generator-filter efficiency

The signal samples were produced with a generator filter and store only the events that
passed it. `scaled_sum_weights` therefore sums over the passing events only, and the
efficiency puts back the events the filter removed (docstring of `get_lumixs_weight`).
The filter requirements are written at the top of `sidm/configs/signal_gen_filter_eff.yaml`.

That file holds, for each signal point, one entry per production: `central`, `v10`, and
`repass_5gev` (the input used to derive `v10`). It is generated by
`sidm/scripts/make_signal_gen_filter_eff.py`; do not edit it by hand. The values are under
review in issue #86, so this page quotes none.

`get_gen_filter_eff(dataset, production)` picks the field named by the production tag:

| `production` | field used |
|---|---|
| `"v10"` | `v10.eff` |
| `"central"` | `central.eff` |
| anything else, or `None` | none: returns 1.0 and prints `WARNING: no gen filter efficiency for <sample> ...` once per sample |

A signal point missing from the file also gets 1.0 with the same warning. If you see that
warning for a signal sample, its yields are too high by a factor 1 / (filter
efficiency).

## How `production` reaches the processor

The processor reads `events.metadata.get("production")`, so the tag has to be in the
fileset metadata. It is set from the name of the location file the sample was found in,
by `utilities.get_production`:

| location file in `sidm/configs/ntuples/` | tag |
|---|---|
| `signal_2mu2e_v10.yaml`, `signal_4mu_v10.yaml` | `v10` |
| `ffntuples.yaml` | `central` |
| any other | `None` |

**Notebook and dask path.** `utilities.make_fileset(samples, ntuple_version,
location_cfg=...)` puts `production` into each sample's metadata, next to `is_data`,
`year` and `skim_factor` from the same YAML entry. Note the default
`location_cfg="signal_v8.yaml"`, which has no tag: always name the location file. A
fileset you build by hand has no tag unless you add one, as `01_first_run.ipynb` does.

**Condor path.** Each job runs `condor/run_sidm_chunk.py`, whose `sample_metadata`
searches every YAML in `sidm/configs/ntuples/` for an entry with the job's sample name
whose directory holds the first file of the job's file list, and takes `skim_factor`,
`is_data`, `year` and `production` from it. If no entry matches, the job prints
`WARNING: no location YAML lists <sample> with these files` and runs as 2018 simulation
with `skim_factor` 1 and no production tag.

**After the run.** `process` records each chunk's tag in
`out[sample]["metadata"]["production"]`. `postprocess` uses the tag only if every chunk of
the sample carried the same one; otherwise it uses `None`, and the metadata keeps every tag
it saw. It prints the efficiency and tag it used
(`<sample> is simulation. Scaling ... (gen_filter_eff = ..., production ...)`) and stores
the efficiency in `out[sample]["metadata"]["gen_filter_eff"]`.

## Condor: per-job normalization and the merge

On Condor every job runs `postprocess` on its own files, so each chunk output is scaled
with the `scaled_sum_weights` of that chunk only. Adding the chunks as they are would
multiply the yields by roughly the number of chunks.
`sidm/scripts/merge_coffea_chunks_eos.py`, function `combine_normalized_chunks`, undoes
this: it multiplies each chunk's cutflows (and histograms, unless they are unweighted) by
that chunk's `scaled_sum_weights`, adds the chunks, and divides by the total. Data chunks
are added as they are. On the notebook and dask paths `postprocess` runs once on the
whole sample, so no merge correction is needed.

The merge calls `check_chunk_normalization` on the chunks of each sample, and stops
without writing an output if it fails. (The command-line script reads the chunks one at a
time, so a chunk that disagrees is found when it is read.)
For each key in `NORMALIZATION_KEYS` (`gen_filter_eff`, `production`, `unweighted_hist`):

- a chunk that has the key must hold exactly one value;
- all chunks of a sample must agree on the value;
- a key present in some chunks and missing in others is refused. Chunks that all lack it
  (outputs older than the key) are accepted.

A failure stops the merge with `<sample>: chunks disagree on <key> (value or presence);
not merging (re-run the odd chunks with the same setting)`. For old outputs without the
`unweighted_hist` key, the merge assumes weighted histograms and warns; pass
`--unweighted-hist` if they were unweighted. The Condor workflow itself is described in
`condor/README.md`.

## What to check on your own outputs

- The `postprocess` line for each signal sample names the production you expect, and no
  `no gen filter efficiency` warning appears for it.
- `out[sample]["metadata"]["gen_filter_eff"]` and `["production"]` each hold one value.
- Signal yields are for 1 fb unless you scaled them yourself.
- `lumi` is the 2018 value: `run_periods.yaml` has no other year.
